워드 임베딩 개요 — 단어를 숫자 벡터로

컴퓨터는 정말 단어의 의미를 알고 있을까? 단어를 어떤 숫자로 바꿔야 뜻까지 담을 수 있을까?

컴퓨터는 글자를 직접 계산하지 못해요. 단어를 숫자 벡터로 바꿔야 하고, 잘 바꾸면 "왕 − 남자 + 여자 = 여왕"처럼 뜻의 관계까지 계산돼요. 이 쪽은 원핫과 워드 벡터, 둘의 비용 차이, 그리고 임베딩을 만드는 4단계를 봅니다.

② 희소 대 밀집

원핫은 어휘가 늘수록 차원·메모리·빈칸이 함께 늘고 모든 단어가 같은 거리다. 임베딩은 차원을 300 안팎으로 고정하고, 뜻이 비슷하면 가깝게 둔다.

③ 4단계와 고려사항

임베딩은 전처리 → 어휘집 → 학습 → 적용 순으로 만든다. 차원은 너무 낮으면 정보를 잃고 너무 높으면 과적합·계산 비용이 커서 보통 100~300을 쓴다.

④ 다음 쪽

단어의 중요도를 숫자로 매기는 가장 단순한 방법은 무엇일까? 많이 나오면 중요할까?

1원핫과 벡터

단어를 숫자로 — 원핫 인코딩과 워드 벡터

방법: 원핫 인코딩 · 워드 벡터(밀집 표현)일상: 단어 사전 만들기

원핫 인코딩은 어휘 크기만큼 긴 벡터에서 그 단어 자리만 1, 나머지는 0으로 써요. 단어가 늘면 벡터도 길어지고(5×5 → 7×7 → 9×9), 모든 단어가 서로 똑같이 떨어져 있어요. 워드 벡터는 차원을 고정하고 뜻의 관계를 거리로 담습니다.

이 칸에서 가져갈 한 가지

원핫은 단어 수만큼 길고 뜻을 모른다. 워드 벡터는 100~300칸으로 고정되고, 뜻이 가까운 단어를 가까이 놓는다.

왜 이 방법을 쓰나

문제 상황

리뷰 분석 모델에 단어를 넣으려면 숫자로 바꿔야 해요.

앞 방법의 한계

원핫은 단어 10만 개면 벡터도 10만 칸이고 99.999%가 0이에요. "개"와 "고양이"의 거리 = "개"와 "자동차"의 거리라 뜻을 모릅니다.

해법

300칸 내외의 촘촘한 벡터를 학습해, 비슷한 문맥의 단어(개·고양이)는 가깝게, 다른 단어(자동차)는 멀게 놓아요(분산 가설, 6회차).

쉽게 말하면 전화번호부 순번(원핫) 대신 "지도 위의 위치"(워드 벡터)로 단어를 적는 거예요. 위치가 가까우면 뜻도 가까워요.

수식이 궁금하면 펼쳐 보기 — 수학 수식을 어려워하는 조수가 대신 물어봅니다

원핫이 메모리를 얼마나 낭비하는지 숫자로 보여 줄 수 있어요?

학교 수학으로 보면 중학교 수학의 거듭제곱(10⁵ × 10⁵ = 10¹⁰)과 단위 환산이에요.

원핫 표 = 어휘 수 × 어휘 수 칸 · 워드 벡터 표 = 어휘 수 × 300칸 · 칸 하나 = 실수 4바이트
어휘 수 V서로 다른 단어의 수
300워드 벡터의 차원(보통 100~300)
4바이트실수 하나를 저장하는 크기(32비트)
숫자로 한 번 해 보기V = 100,000이면 원핫 표: 10⁵ × 10⁵ × 4 = 4 × 10¹⁰바이트 = 40 GB워드 벡터 표: 10⁵ × 300 × 4 = 1.2 × 10⁸바이트 = 120 MB원핫 벡터 하나에서 0인 칸: 99,999 ÷ 100,000 = 99.999%

300분의 1 크기인데 뜻까지 담는다니! 원핫은 거의 전부 0이라 낭비였네요.

일상으로 치면

전화번호부 순번으로는 "김 씨"와 "김 씨 동생"이 가까운지 알 수 없어요. 지도 위 집 위치를 알면 가까운 이웃을 바로 찾죠.

자연어 처리로는

원핫 인코딩은 메모리 낭비, 모든 단어 간 거리 동일, 희소성, 의미 관계 표현 불가라는 한계가 있어요. 워드 임베딩은 저차원(300 내외) 밀집 벡터로 바꿔 유사한 단어를 가깝게 배치하고, "왕 − 남자 + 여자 ≈ 여왕" 같은 벡터 연산도 가능하게 해요(교안). 대표 기법: 빈도 기반(TF-IDF), 예측 기반(Word2Vec·GloVe), 문맥 기반(BERT·ELMo), 토픽 기반(LDA·LSA).

박사

어휘 수를 늘려 보고, 표현 방식을 원핫과 워드 벡터로 바꿔 보세요.

조수(하루)

그림의 2차원 좌표는 관계를 보이려는 예시값이에요. 메모리는 4바이트 실수로 계산했어요.

실험 — 원핫 대 워드 벡터 — 크기와 거리

자세한 풀이 — 전처리부터 임베딩까지 4단계(교안) (펼쳐 보기)
  1. 1단계 텍스트 전처리: 불용어 제거, 어간·표제어 추출, 품사 태깅·개체명 인식(2~3회차).
  2. 2단계 어휘 집합과 인덱스: 고유 단어를 모아 번호를 붙이고, 최소 등장 횟수로 거르고, PAD·UNK 같은 특수 토큰을 더해요.
  3. 3단계 임베딩 학습: 목적 함수(문맥 예측·동시 출현)를 정하고 차원(보통 100~300), 학습률·배치 크기·반복 횟수를 조정해요.
  4. 4단계 활용: 문서 분류, 감성 분석, 개체명 인식, 검색·추천에 쓰고, 사전 학습된 임베딩을 미세조정해 쓰기도 해요.
  5. 평가: 단어 유사도·추론 과제(내재적), 실제 과제 성능(외재적). 너무 낮은 차원은 정보 손실, 너무 높으면 과적합과 계산 비용.

이 칸의 한계 · 워드 벡터는 단어의 뜻을 담지만, "이 리뷰에서는 어떤 단어가 핵심인가"는 문서 안 빈도와 전체 문서에서의 희귀도를 따져야 알 수 있어요.

업무에 쓸 때 알아 둘 것 (펼쳐 보기)

데이터 분석으로 치면

추천 시스템에서 상품명·리뷰를 벡터로 바꾸면 비슷한 상품을 거리로 찾을 수 있어요(교안 사례).

임베딩은 학습 데이터를 닮아요. 데이터가 적거나 치우치면 편향된 벡터가 생겨요(6회차).

2희소 대 밀집

원핫의 값 — 메모리, 빈칸, 그리고 모두 같은 거리

비교: 원핫 인코딩 대 워드 임베딩수학: 두 점 사이 거리(피타고라스)

교안은 원핫 인코딩의 문제를 네 가지로 정리해요. 단어가 10만 개면 벡터도 10만 차원이라 메모리를 낭비하고, 한 칸만 1이라 99.999%가 빈칸이고, 모든 단어 사이 거리가 같아 "개·고양이"와 "개·자동차"를 구별 못 하고, 그래서 의미 관계를 담을 수 없어요. 워드 임베딩은 300차원 안팎의 밀집 벡터로 이를 풀어요.

이 칸에서 가져갈 한 가지

원핫은 어휘가 늘수록 차원·메모리·빈칸이 함께 늘고 모든 단어가 같은 거리다. 임베딩은 차원을 300 안팎으로 고정하고, 뜻이 비슷하면 가깝게 둔다.

왜 이 방법을 쓰나

문제 상황

쇼핑몰 리뷰 어휘가 5만 개예요. 단어마다 숫자 묶음을 줘야 컴퓨터가 계산할 수 있어요.

앞 방법의 한계

원핫으로 하면 단어 하나가 5만 칸짜리 벡터가 되고, 그중 4만 9,999칸이 0이에요. 게다가 어떤 두 단어든 거리가 똑같아요.

해법

300칸 정도의 벡터에 모든 칸을 의미 있는 숫자로 채워요. 비슷한 단어는 가깝게, 다른 단어는 멀게 배치해요.

쉽게 말하면 5만 명에게 각자 5만 칸짜리 출석부를 주는 대신, 키·나이·사는 곳 같은 300가지 특징 카드를 주는 거예요.

원핫 두 단어 사이 거리가 왜 늘 1.414예요?

학교 수학으로 보면 피타고라스 정리(두 점 사이 거리, 중학교)

거리 = √(차이₁² + 차이₂² + … )
개(1, 0, 0, …)
고양이(0, 1, 0, …)
차이첫 칸 1, 둘째 칸 1, 나머지 0
숫자로 한 번 해 보기개와 고양이: √(1² + 1² + 0 + …) = √2 ≈ 1.414개와 자동차: 역시 두 칸만 달라 √2 ≈ 1.414→ 어떤 두 단어든 같은 거리

칸이 아무리 많아도 서로 다른 칸 두 개만 1이니까 거리가 똑같을 수밖에 없네요.

일상으로 치면

5만 칸 출석부에 자기 칸 하나만 체크하면 누가 누구와 비슷한지 알 수 없어요. 특징 카드라면 비슷한 사람끼리 모을 수 있죠.

자연어 처리로는

원핫: 메모리 낭비, 모든 단어 간 거리 동일, 데이터 희소성(한 자리만 1), 의미 관계 표현 불가. 워드 임베딩: 300차원 내외 저차원, 유사 단어는 가까이, 밀집 표현(모든 칸이 정보), "왕 − 남자 + 여자 = 여왕" 같은 벡터 연산 가능(교안 비교).

조수(하루)

칸 하나를 4바이트(소수 한 개)로 계산한 설명용 값이에요.

실험 — 원핫 대 임베딩 — 메모리, 빈칸, 거리

자세한 풀이 — 원핫 인코딩의 한계와 워드 임베딩의 해결책(교안) (펼쳐 보기)
  1. 메모리 낭비: 단어 10만 개면 벡터도 10만 차원 → 워드 임베딩은 300차원 내외로 압축해 메모리와 연산을 줄여요.
  2. 모든 거리가 같음: "개·고양이" = "개·자동차" → 임베딩은 뜻이 비슷하면 가깝게 배치해요.
  3. 희소성: 한 자리만 1, 나머지는 0 → 임베딩은 모든 칸에 정보가 있는 밀집 표현이에요.
  4. 의미 관계 불가: "왕"과 "여왕"의 관련성을 모름 → 임베딩은 "왕 − 남자 + 여자 = 여왕" 같은 연산이 돼요.

이 칸의 한계 · 밀집 벡터가 좋다는 건 알았는데, 그 300개 숫자는 어떻게 정할까요? 전처리부터 학습·적용까지 4단계가 필요해요. 다음 칸이에요.

34단계와 고려사항

워드 임베딩 만들기 4단계 — 그리고 성공을 위한 고려사항

절차: 전처리 → 어휘집 → 학습·최적화 → 적용고려: 데이터 · 차원 · 평가

교안은 워드 임베딩을 4단계로 정리해요. ① 텍스트 전처리 ② 어휘 집합 구축과 인덱싱 ③ 임베딩 학습과 벡터 최적화 ④ 실무 적용. 그리고 성공하려면 데이터 품질, 알맞은 차원(보통 100~300), 평가 방법을 챙기라고 해요.

이 칸에서 가져갈 한 가지

임베딩은 전처리 → 어휘집 → 학습 → 적용 순으로 만든다. 차원은 너무 낮으면 정보를 잃고 너무 높으면 과적합·계산 비용이 커서 보통 100~300을 쓴다.

왜 이 방법을 쓰나

문제 상황

회사 상담 기록으로 우리만의 단어 벡터를 만들고 싶어요. 어디서부터 해야 할까요?

앞 방법의 한계

데이터를 그대로 모델에 넣으면 어휘가 수십만 개로 불어나고, 처음 보는 단어를 처리할 방법이 없고, 차원을 아무렇게나 정하면 성능이 들쭉날쭉해요.

해법

전처리로 다듬고, 최소 등장 횟수로 어휘집을 줄이고 UNK 같은 특수 토큰을 두고, 차원·학습률을 조정하며 평가한 뒤 실제 과제에 써요.

쉽게 말하면 요리 전에 재료 손질(전처리) → 재료 목록 정리(어휘집) → 맛보며 간 맞추기(학습·최적화) → 손님상에 내기(적용)예요.

일상으로 치면

식당은 재료를 손질하고, 재료 목록에 번호를 붙이고, 맛을 보며 간을 맞춘 뒤 상에 내요. 목록에 없는 재료가 오면 "기타" 칸에 넣죠.

자연어 처리로는

① 전처리: 불용어 제거, 어간·표제어 추출(running → run), 품사 태깅·개체명 인식. ② 어휘집: 빈도 필터(최소 등장 횟수), 어휘 크기 제한, 특수 토큰(PAD 빈자리 채움, UNK 모르는 단어, SOS 문장 시작, EOS 문장 끝). ③ 학습: 목적 함수(문맥 예측·동시 출현), 차원 100~300, 학습률·배치·반복 조정. ④ 적용: 문서 분류·감성 분석·개체명 인식, 유사도로 검색·추천, 사전 학습 임베딩 + 미세조정(교안).
